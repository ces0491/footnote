# Synthetic data

Footnote runs on a fictional league generated by code in `src/footnote/generator`. Nothing in it
comes from real matches: clubs, players, officials and every event are synthetic. This page covers
what the generator produces, how a match is simulated, the formats services consume, and how the
showcase match from [experience.md](experience.md) is found.

## What it produces

- **The league**: 20 clubs with names, grounds, colours, formations and a hidden style and
  strength each; 25-player squads; 12 referees. A seed fixes all of it (`--seed`, default 2026).
- **A match**, as four files:
  - `meta.json`: competition, kick-off, venue, referee, line-ups and attacking directions;
  - `feed.jsonl`: the event feed, one JSON message per line, in publication order;
  - `tracking.npz`: every player and the ball at 10 frames a second (optional);
  - `answer_key/<match_id>.json`: the hidden truth, kept apart from the feed.
- **A season**: all 380 fixtures, each match regenerable on its own from the league seed and its
  match ID.

The answer key holds what a live data provider wouldn't know: the hidden match state at every
moment, the true probability behind each pass, shot, tackle, duel and carry, offside margins,
whether an arm was in an unnatural position, the true goalscorer, each club's strength and style,
the attributes of every player in both match-day squads, and each correction the feed will make
(`corrections`). The match-state model is fitted on its states, and the models built on the feed are
scored against it.

## How a match is simulated

**Hidden match state.** At any moment the match is in one of five regimes, eight once the side
holding one is counted: one side in *control* (settled possession, the other side not pressing
high), one side applying sustained *pressure* (camped in the opponent's half), one side in
*transition* (breaking at speed after a regain), *chaos* (neither side controls; the ball changes
hands often) or *balanced*. Regimes
follow a semi-Markov process: each is entered with a planned duration, and the next is drawn with
weights from both teams' styles and strengths, the score and the clock. A regain can start a
transition for the side that won the ball; when the break ends, the regime it interrupted resumes.
The regime is never written to the feed. It changes how both teams play (block height, pressing,
risk, tempo, long balls, crossing, shot appetite), and the events and the tracking are the only
evidence of it.

**Players.** Each team keeps its formation inside a block positioned by the ball, possession,
style and regime. Defenders are pulled goal-side of nearby attackers. Strikers hold the shoulder
of the last defender with an error in the timing of their runs, which is where offsides come from.
Players move towards their targets with each player's top speed and acceleration, and tire over
the match. Each side makes three to five substitutions in up to three windows, taking off its
least durable starters; a substitute stays on once he's come on.

**Decisions.** The player on the ball weighs every pass (to feet and into space), shot, carry,
cross and clearance in one currency, the chance of a goal: the threat of where the ball ends up
times the chance of getting it there, less the threat handed over if it goes wrong. The team's
style and the regime weight progress against safety, and a softmax picks the action, so better
decision-makers choose well more often.

**Outcomes.** Each outcome is drawn from an explicit probability model: pass completion from
distance, height, how many opponents can cut out the ball and how tightly the receiver is marked,
headed passes included; a cross from whether it gets past the nearest defender, reaches the zone,
beats the keeper and wins the header there; shots from distance, angle, pressure, defenders in the
way and the shooter and keeper; tackles and duels from the players' attributes; whether a carry is
closed down from the carrier's dribbling and the pressure around him. The probability used is
stored in the answer key with the event.

**Officials.** Offside is judged from everyone's position at the moment the ball is played, for
passes, crosses and headers alike. The assistant referee sees it with error; close calls in
promising attacks are held (the delayed flag) for VAR to decide if a goal follows. VAR reviews
goals for offside and fouls in the build-up, every penalty, and handball claims, where the arm
position is part of the hidden truth. Cards, advantage and added time follow from the play.

**The provider layer.** The simulation's raw events become feed messages with stable event IDs,
club and player IDs, the match clock and a wall-clock timestamp, and the truth moves to the answer
key. Like a real provider, the feed is sometimes wrong at first: a goal that took a deflection can
be credited as an own goal and corrected a few minutes later with an `amendment` message, and now
and then a goal recorded without an assist is given one after review, three to ten minutes later.
The match clock stops at each whistle, so a correction issued at half-time or after the match
carries the clock of the whistle before it, and its `ts` says when it was issued.

## The feed

Every message validates against the pydantic models in `src/footnote/generator/schema.py`, which
forbid unknown fields; `python -m footnote.generator schema` prints the JSON Schema.

**Common fields**: `feed_version`, `match_id`, `seq` (publication order from 1), `ts` (UTC),
`event_id`, `version`, `period`, `t` (seconds since the period kicked off), `clock` (match seconds;
the second half starts at 2700), `minute` (as shown on screen: the 23rd minute runs from 22:00) and
`added_minute`. On-ball events add `possession`, `team_id`, `player_id`, `x` and `y`.

**Coordinates** are metres in one absolute frame: x along the pitch from 0 to 105, y across from 0
to 68. The home side attacks towards x = 105 in the first half; `meta.json` records each side's
direction per half.

| Type | What it records | Notable fields |
| --- | --- | --- |
| `match_info` | first message: competition, line-ups, referee, pitch | `info` |
| `period_start`, `period_end`, `match_end`, `added_time` | the clock | `score`, `minutes` |
| `pass` | every pass, including restarts, crosses and headers | `outcome`, `recipient_id`, `pass_type`, `body_part`, `height`, `cross`, `through_ball`, `length`, `speed_kmh`, `end_x`, `end_y`, `freeze_frame` (receiver offside) |
| `carry` | running with the ball | `end_x`, `end_y`, `duration` |
| `pressure` | a defender closing the carrier down | `target_id` |
| `tackle`, `duel`, `interception`, `ball_recovery`, `block`, `clearance` | contests for the ball | `opponent_id`, `outcome`, `duel_type` |
| `shot` | every shot | `outcome`, `body_part`, `shot_type`, `play_pattern`, `set_piece`, `speed_kmh`, `distance`, `freeze_frame` |
| `goalkeeper` | saves and claims | `action`, `outcome` |
| `goal` | a goal as first recorded | `player_id`, `assist_id`, `own_goal`, `header`, `score`, `from_event_id` |
| `foul`, `card` | fouls, cautions and dismissals | `fouled_id`, `advantage`, `penalty`, `card`, `reason` |
| `offside` | the flag | `pass_event_id`, `delayed_flag` |
| `ball_out` | the ball leaving the pitch | `restart` |
| `var_check` | a check starting and completing | `check`, `incident`, `on_field_decision`, `decision`, `overturned` |
| `substitution` | a change of players | `team_id`, `player_off_id`, `player_on_id`, `half_time`, `reason` |
| `possession_change` | the ball changing sides | `team_id`, `from_team_id`, `cause`, `x`, `y` |
| `injury`, `woodwork` | a fouled player down injured, stopping play; the ball hitting the post or bar | the on-ball fields only |
| `amendment` | a correction to an earlier event | `event_id` and `version` of the corrected event, `amends` (the corrected event's type), `changes`, `reason`, `corrected_event` |

A goal that VAR rules out stays in the feed; the `var_check` that completes with `decision:
"no_goal"` names it in `goal_event_id` and restates the score. Shots, penalties the referee gives
on the field, and the start of a VAR check for handball or a missed penalty carry a `freeze_frame`
with every player's position and the ball. Offside is judged when the ball is played, so a flag
(and a VAR offside check) points to its pass through `pass_event_id`, and that pass carries the
freeze frame.

`shot_type` says whether a shot was a penalty, a direct free kick or anything else; where the move
began is in `play_pattern`. A goal's `from_event_id` is the shot it came from, or for an own goal
headed in from a cross, the cross.

## Tracking

`tracking.npz` holds `period`, `t`, `players_cm` (frames × 22 slots × 2, int16 centimetres, with
-32768 for an empty slot), `ball_cm` (x, y, z), `occupancy`, `slot_players` and `frame_rate`.
Slots 0–10 are the home side and 11–21 the away side in formation order;
`slot_players[occupancy[f]]` names the player in each slot at frame `f`, which changes with
substitutions. `Tracking.load()` decodes it to metres.
Player paths pass through the simulation's keyframes, so tracking and freeze frames agree, and no
player moves faster than 10.5 m/s between frames; `tests/test_match.py` checks both. The processor
reads the showcase's tracking against each event's clock, standing in for a tracking feed: positions
for pass difficulty, each side's shape for the match state, and distances and speeds
([models.md](models.md)).

## The showcase match

[experience.md](experience.md) tells the story of Saltmarsh Rovers v Kingsferry Athletic.
`showcase.py` finds the match by search: it runs the simulation beat by beat, and at each beat tries
reseeded continuations from a snapshot until the beat happens. Rare beats are found in stages: for
the 31st minute, Varlan on the ball more than 55 m from his own goal line, then a pass to Dellow in
an unflagged offside position, then Dellow scoring. Between beats nothing may be scored, nobody may
be sent off, and VAR checks happen only at 31' and 74'.

| Beat | Required |
| --- | --- |
| 0–21' | Saltmarsh in control at least 60% of the time, with three shots or more to Kingsferry's one at most; no Kingsferry counter-attack yet |
| 23' | Kingsferry score from their first counter-attack |
| 31' | Dellow scores from a Varlan pass; VAR rules it out for offside |
| 38–45' | Saltmarsh applying sustained pressure at least half the time, with three shots or more |
| 52' | Varlan scores from 20 m or more, with Saltmarsh in control or pressing |
| 63–68' | chaos at least 60% of the time |
| 74' | a handball claim in Kingsferry's box; VAR says no penalty |
| 81' | Adeyani scores on a Kingsferry break, the shot deflected off Penhallow |
| 84' | the goal, first credited as a Penhallow own goal, is amended to Adeyani |

Two things are set by hand: the provider's first call on the 81st-minute goal, which is told to
credit the deflection as an own goal and amend it at 83:20 on the clock, and the named players, who
are never substituted. Every other event is a draw from the same model as any other match; the
search only chooses which draws to keep. The accepted path is saved in `data/showcase_recipe.json`
as the step and seed of each reseed. The match it produces is committed too (`data/league.json`,
`data/matches/fl-2627-showcase-sal-kin/` and its answer key). The services deploy the league and
match files, with the answer key left out of the image, so nothing regenerates the showcase in the
cloud. `tests/test_showcase.py` replays the recipe, checks the story still holds and checks the
committed files are the replayed match. A change to the generator invalidates the recipe: rerun the
search, which rewrites the showcase files, and commit both.

## Reproducing the data

```sh
uv run python -m footnote.generator league               # data/league.json and its answer key
uv run python -m footnote.generator showcase             # replay the showcase recipe, with tracking
uv run python -m footnote.generator showcase --search    # find a new recipe (several minutes)
uv run python -m footnote.generator season --workers 8   # all 380 fixtures
uv run python -m footnote.generator match SAL KIN --tracking
uv run python -m footnote.calibration                    # regenerate docs/calibration.md
```

Output goes to `data/`. Git keeps the league and the showcase match with their answer keys, the
recipe, the name check and the agents' recorded evaluation run (`data/evals/drafts.json`, written by
`python -m footnote.evals live --record`); everything else there is rebuilt from seeds.

## Calibration

The generator was tuned against published Premier League figures for 2025/26: goals, results,
shots, passes, set pieces, discipline, VAR overturns, ball-in-play time, distance covered and top
speeds. [calibration.md](calibration.md) compares two full generated seasons, under different league
seeds, with each figure, names its source and lists the gaps that hold under both seeds.

## Names

Club names were chosen by hand and player and official names are built from syllables, so a clash
with a real person's name is unlikely but possible. `scripts/check_names.py` looks up every full name
in Wikidata for exact matches with real people, and every club and place name for real football
clubs, and writes `data/name_check.json`. Names that matched a real person are blocked in
`names.py` and never generated; `tests/test_names.py` fails if a name is unchecked or matches.
Wikidata doesn't list every lower-league player, so a clear result can still miss one. The showcase
cast were also checked by web search. Two club cautions remain, neither a football club: Saltmarsh
is a family name and the name of two hamlets, and Vellacott is a family name.
